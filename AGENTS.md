Never edit swagger.json and src/caretogether-pwa/src/GeneratedClient.ts, they are auto generated on build time.
When backend API/client contracts change, always run dotnet build to regenerate swagger.json and src/caretogether-pwa/src/GeneratedClient.ts instead of creating manual frontend shims, duplicated enum values, or temporary compatibility types.
When possible, use functional programming approach and "object calisthenics" (like early returns) for better readability and safeness.
Use the `ph-unmask` class only for text that is safe to send to PostHog. Any text without a `ph-unmask` ancestor should be treated as sensitive and masked from analytics capture. Place `ph-unmask` as close as possible to the component or element that renders the actual safe text, instead of applying it high in the tree, so unrelated sensitive content is not accidentally unmasked.
When working with PostHog early access feature switches, follow docs/early-access-features.md.
[E2E feature flags](docs/e2e-feature-flags.md) explains how Playwright supplies deterministic PostHog flag values without changing normal development behavior.
When a `DataGridPremium` uses `usePersistedGridFilterModel`, render it with `src/caretogether-pwa/src/Generic/PersistedFilterDataGridPremium.tsx` and pass `filterModel`, `filterModelRestored`, and `onFilterModelChange` from the hook. This keeps a restored quick filter visible when the grid mounts.

Keep Playwright E2E tests focused on critical user journeys: authentication and access control, creating or editing records (families, referrals, arrangements, approvals), policy configuration, and data shown in grids that staff rely on. Do not add E2E tests for cosmetic or low-risk UI affordances (layout and spacing, toggles like fullscreen, icons, tooltips, responsive variants) unless the task explicitly asks for one. Before adding a new spec, prefer extending an existing spec for the same feature; never add a new CI workflow step for a single spec. Do not build per-component harnesses that mock out sibling components just to make something E2E-testable. If the logic is worth testing, extract it into a pure function and cover it with a `*.test.ts` unit test (`npm run test:unit`). When a change has no E2E coverage by this rule, say so in the PR description and list the manual check performed.
